# 沉淀

## 什么该进 DStack

三个条件都满足才收：

1. **与内容无关。** 换一个完全不同的项目仍然适用。产品是什么、用什么设备、选了哪个库，都属于内容，留在项目自己的仓库里。
2. **有出处。** 来自一次真实发生的事：哪里出了问题、花了多少代价、后来怎么解决的。凭空想到的好习惯不收。
3. **能照着做。** 写得出具体的步骤或判断标准。只能写成"要注意某某"的不收。

不确定是否与内容无关时，试着把例子里的专有名词全部换掉。换完规则还成立，就是方法。

## 做法

1. **回顾这段工作，找三类时刻**：
   - 返工：做完又推倒重来的地方。早一点知道什么就能避免？
   - 意外：实际情况和预期不一样的地方。当时依据的是什么？
   - 被纠正：用户否决或改正助手的地方。助手默认的做法哪里不对？
2. **每个时刻写成一条规则**：在什么情况下、做什么、为什么。
3. **先找现有技能。** 能并入现有技能的就加一条，不新建。新建技能的条件是它有独立的触发场景。
4. **去掉内容。** 例子改写成不含项目名、产品名、人名的通用说法。
5. **提交到 dstack 仓库**，提交信息写明这条经验的来源类型（返工、意外、被纠正），不写项目名。

## 技能的写法

- 文件在 `skills/<名称>/SKILL.md`，名称用英文小写加连字符。
- 开头的 description 写清两件事：这个技能做什么，什么时候该用它。
- 正文按"为什么、做法、规则"组织，尽量短。
- 需要调用 gstack 或 pstack 时，写明具体是哪个技能，不重新描述它们已有的流程。

## 规则

- **只增加用得上的。** 一条规则半年没被用到，就删掉。
- **规则之间冲突时**，把冲突写出来请用户定，不自行取舍。
- **改版本号**：新增技能改次版本号，修改现有技能改修订号，写进 CHANGELOG。
- 秘密、内部地址、客户信息任何时候都不进这个仓库。
