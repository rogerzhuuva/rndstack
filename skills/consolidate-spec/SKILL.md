# 合并定稿

## 为什么

多轮评审通常以追加的方式记录修改：每轮在文末加条目，后面的条目取代前面的。评审中这样做是对的，因为能看出每条修改从哪来。但评审结束后，这份文档已经没法照着实现了：同一条规则有三四个版本，读的人必须从头读到尾才知道哪个算数。

把合并当作开始实现的前置条件，而不是一项可以并行的任务。

## 做法

1. **存档原文。** 把带完整评审记录的文档整体移到 `docs/designs/archive/<日期>-<名称>-review-record.md`，用 `git mv` 保留历史。
2. **重写正文。** 新文档只有一个正文，按主题分节，不按评审轮次。
3. **逐条归位。** 每条已接受的修改放进它所属的那一节。有取代关系的只写最终的说法。
4. **事实修正放最前。** 评审中核实到的、推翻了原前提的事实，写在约束或事实一节里，带依据。
5. **用户的决定原样保留**，包括用户否决的建议。被否决的建议写在"不在范围内"一节，一两句即可，理由指向存档。
6. **结尾保留评审结论。** 评审工具要求的报告节放在文档最后。

## 检查

合并后的文档里不应该出现：

- "取代""以本条为准""此前的说法"这类字样
- 同一个数值的两个不同取值
- 只在存档里出现、正文里找不到的已接受要求
- 历史审阅意见

## 规则

- **不借合并夹带新内容。** 合并只是整理，不新增要求，不删除已接受的要求。发现需要新决定的地方，单独提出来。
- **为了能照做而补的具体细节单列一节。** 评审只给了方向（"定几种类型""内容要充实"），合并时不得不写成具体的清单或数值。这些写进正文，同时在文末逐条列出，由主持评审的一方过目并写明裁决。
- **合并后的文档没有经过独立审阅，要明说。** 它是整理出来的，不是评审过的。
- 存档文件不再修改。
- 提交信息写明这是合并定稿，方便以后在历史里找到分界点。
