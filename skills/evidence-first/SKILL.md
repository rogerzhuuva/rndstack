# 事实先行

## 为什么

功能列表说的是"能做什么"，不说"怎么调用"。一个库的说明里分开列出五项功能，实际接口可能是一次调用全部完成。如果按功能列表去设计动作、状态和逐步结果，整个模型的形状都是错的，而且文档评审发现不了，因为评审只读文档。

## 做法

1. **列出设计所依赖的每个外部接口。** 每个写一行：我们假设它是什么样的。
2. **按可信程度从高到低找依据**，找到一层就停：
   - 源码或类型定义
   - 仓库里的可运行示例
   - 官方接口文档
   - README 的功能列表
   - 第三方文章或检索摘要
3. **读最小的一份真实代码。** 通常是 examples 目录里的一个文件，几分钟就够。
4. **写一页事实记录**，放进仓库。每条事实包含：
   - 事实本身（方法名、参数次序、返回什么、有没有事件）
   - 依据（文件路径或链接、读取日期、版本或提交号）
   - 依据类型：读过源码 / 读过示例 / 读过文档 / 只看了摘要 / 实测过
5. **对照假设。** 不一致的地方先改设计，再继续。
6. **锁定版本。** 把依赖固定到读过的那个提交或版本。

## 规则

- 没有依据的陈述标"未核实"，并在设计里计数。未核实不等于错，但不能当作已知。
- "只看了摘要"和"读过原文"分开标。引用的数字尤其如此。
- 发现自己之前说错了，在记录里写更正，不悄悄改掉原话。
- 接口形状没核实之前，不冻结数据格式。可以先做不依赖它的部分。
- 真机或线上才能验证的事，写成明确的待办和记录模板，不写成结论。

## 完成的标志

事实记录里，设计依赖的每个接口都有一条达到"读过示例"或更高的依据，或者被明确标为未核实并有对应的待办。
